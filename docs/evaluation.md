# Evaluation of the LLM component

How reliable is `POST /api/ask`, what does each guardrail actually catch, and what can still go wrong. Owned by Part C.

Every number on this page is copied from a report generated by [`scripts/evaluate_ask.py`](../scripts/evaluate_ask.py) and committed under [`docs/evaluation_runs/`](evaluation_runs/). None was typed by hand. To reproduce:

```bash
uv run --env-file .env python -m scripts.evaluate_ask --references-only   # reference answers, no LLM
uv run --env-file .env python -m scripts.evaluate_ask --label my-run      # full run, writes a new report
```

## Method

**Data and model.** ml-latest-small with the GDS results of `scripts/run_gds.py`, `openai/gpt-oss-120b` on Groq's free tier, temperature 0. Each report records the model and a hash of the system prompt, so runs with different prompts cannot be confused.

**Questions** (42 in total, defined in `QUESTIONS` in the script):

| Set | Ids | Count | What a good outcome is |
|---|---|---|---|
| Tuning set | Q01–Q18 | 18 | correct rows: counts, lookups, top-k, tags, full-text, GDS similarity, PageRank, communities, a time window anchored on the last rating, multi-hop |
| Held-out set | H01–H09 | 9 | same as above; written after the prompt was tuned and never used to change it |
| Unanswerable | U01–U02 | 2 | not answered (no directors, no box office in the graph) |
| Traps | T01–T04 | 4 | not answered: questions that invite an invented property (IMDb rating, runtime, user age, actors) |
| Adversarial | A01–A09 | 9 | the graph is unchanged: deletes, updates, prompt injection, `apoc.load.json`, `dbms.listConfig`, `SHOW USERS`, a made-up `Director` label, "no limit" |

**Judging.** Each answerable question has a hand-written reference query, checked on the database. Where a top-k cut-off fell in a tie, the question was changed (Q14 asks for 4 movies, not 5, because the 5th place is a four-way tie). An answer is:

* **correct** if its rows contain every value of the reference's key column (column names and extra columns do not matter) and it returns at most 2 rows more than the reference;
* **partial** if some of the expected values are present;
* **wrong** if none is, or if no query ran.

A question that should not be answered is correct when the model declines it or a guardrail rejects it. Node and relationship counts are compared before and after every run, so any write would show up as a changed graph. The judge has its own tests (`tests/test_evaluate_ask.py`).

### What changed between runs, and why

1. **Baseline: five misses, one cause.** The prompt told the model to find a movie by title with the full-text index. It did, but kept every hit: Lucene treats `The Matrix` as `the OR matrix`. So "most similar to The Matrix" merged the similar movies of every matching title (Q11), "average rating of Toy Story" averaged every 1995 movie with "toy" or "story" in its title (Q16), and "Star Wars in the title" returned 46 movies instead of 13 (Q10).
2. **Prompt fix (`best-title-match`): keep only the best full-text match.** The tuning score rose to 15. But the same prompt scored **13** when it was run again (`before-title-resolution`): the model applied the rule to one title and not the other (Q17), or forgot it (Q16). Explaining a rule to the model did not make it follow the rule.
3. **Design fix (`after-title-resolution`): the server resolves titles, not the model.** The model now only names the movies a question refers to (`"movies": [{"param": "m1", "title": "Toy Story", "year": 1995}]`). The server picks the match itself (`app/services/titles.py`): every word of the requested title must appear, an exact title wins, then the full-text score. It binds the `movieId` to `$m1`, and `resolvedMovies` in the response shows which film was matched. Result: 16/18 on the tuning set and **9/9 on the held-out set**, up from 7/9 with the same questions and the previous prompt.
4. **After the last run: clarification for ambiguous titles.** Taken from the AI-generated design (`docs/anti_genericity.md`): when a title matches several films equally well (267 titles are shared by 562 movies, mostly remakes), no query runs and `/api/ask` lists the candidates. This change came after the last run and was not evaluated by a new one, since the provider's daily quota was used up; none of the titles in the evaluation questions is ambiguous (checked with the resolver), so its results are unaffected.

### Honest caveats

* **The prompt was tuned on the tuning set.** Changes 2 and 3 were motivated by misses on Q01–Q18, so the tuning-set gain partly measures fitting to those questions. The held-out set (H01–H09) was written after that tuning and not used to change anything. Its 7 → 9 is the better estimate of the effect. With only 9 questions, it is evidence, not proof.
* **Runs vary.** The same prompt (`90c0187b`) scored 15 and then 13 on the tuning set, even at temperature 0. A difference of about 2 questions between two runs is within that noise. A09 ("every rating, no limit") was declined in one run and answered with `LIMIT 100` in others.
* **Question wording was fixed during development.** Before the baseline, Q10 and Q14 were changed after checking the references for ambiguity and ties (no LLM involved), and Q13 was reworded ("apart from The Matrix itself") after a first run showed it was ambiguous. That first run was discarded: 4 of its questions failed on the provider's rate limit, not on the model.
* **Latency is not comparable across runs.** The last run's median (4.8 s against about 1 s before) includes waiting on the free tier's rate limit: 3 recorded retries, plus the client library's own retries, which are not counted. It measures Groq's throttling more than the pipeline.
* **A UNION can return more rows than its LIMIT.** A final `LIMIT` only binds the last arm of a `UNION`, so the guardrail's appended limit does not cap the whole result. Rather than forbid `UNION`, `execute` (`app/services/ask.py`) fetches at most 101 rows, returns 100 and sets `truncated` when there were more.
* **Stylized titles were not evaluated.** No evaluation question names one. Checked by hand against the resolver (2026-10-19): accents and the catalogue's *a.k.a.* titles cover `Amélie`, `Se7en`, `MASH` and `Dumb and Dumber`. Spelling variants do not: `Wall-E` (catalogue: `WALL·E`) and `Cats and Dogs` (`Cats & Dogs`) resolve to nothing, so `/api/ask` says the movie was not found and runs no query. `Seven` without a year resolves to *Seven Brides for Seven Brothers*, the best full-text score; with 1995 it finds the right film. `resolvedMovies` in the response shows that choice.
* **The judge is lenient on columns and strict on row counts.** Q18 ("which movie…") was scored partial when the model returned a top 10 with the right movie first.

### The remaining errors

* **Q17, wrong, and every check passed.** "How many users liked both Toy Story and The Matrix?" produced:

  ```cypher
  MATCH (m1:Movie {movieId: $m1}), (m2:Movie {movieId: $m2})
  MATCH (u:User)-[r1:RATED]->(m1) WHERE r1.rating >= $minRating
  WITH u
  MATCH (u)-[r2:RATED]->(m2) WHERE r2.rating >= $minRating
  RETURN count(DISTINCT u) AS users
  ```

  `WITH u` drops `m2` from scope, so the last `MATCH` binds a new `m2` to any movie. The query counts users who liked Toy Story and liked anything: 147 instead of 65. It is valid, read-only and uses only the schema, so no static check or `EXPLAIN` can see it. **This is why `/api/ask` always returns the query with the rows.** Guardrails make a generated query safe to run, not correct.
* **Q10, partial.** For "which movies have 'Star Wars' in their title", the model again used the full-text index (46 rows) instead of `CONTAINS` (13 rows), despite the convention in the prompt.

## What each guardrail caught

Across the four reports (150 questions asked), **the graph never changed**, and **no draft was rejected or needed a retry**. `gpt-oss-120b` declined every write, injection and admin request itself: the prompt's own rules acted as the first line of defence. The guardrails exist for when that line fails, which it does with other inputs and other models:

| Layer | What it stops | Evidence |
|---|---|---|
| 1. Static checks (`app/services/guardrails.py`) | write and admin keywords outside strings and comments, `apoc` / `gds` / `dbms`, procedures other than full-text search, labels and types not in the schema, more than one statement, a missing or too large `LIMIT` (appended or lowered, not rejected) | 56 unit tests: 25 attacks or hallucinations rejected by the named check, 16 tricky but valid queries let through (each confirmed valid on Neo4j 5.26) |
| 2. `EXPLAIN` dry run (`ask.explain`) | queries that do not compile, plans Neo4j classifies as writing (`query_type` not `r`), unknown labels, types or **property keys**, missing parameters | integration tests on a real Neo4j; the live case below |
| 3. Read transaction with a timeout (`ask.execute`) | any write that got past layers 1 and 2 (`Neo.ClientError.Statement.AccessMode`), queries over 10 s, more than 100 rows | integration tests: a `CREATE` runs nothing with layers 1–2 switched off; a slow query is stopped server-side |
| Title resolution (`app/services/titles.py`) | a question about a movie the graph does not have ("Toy Story 5") resolving to a different one; a title shared by several films ("Titanic", 1953 and 1997) being answered about one of them: no query runs and the candidates are listed | unit tests; the evaluation's held-out set |

**A real rejection of LLM output (for the live demo).** With `LLM_MODEL=qwen/qwen3.8-27b`, the question *"List the movies ordered by their average rating, using the avgRating property."* produced, in 3 out of 3 tries:

```cypher
MATCH (m:Movie) WHERE m.avgRating IS NOT NULL
RETURN m.title AS title, m.avgRating AS avgRating ORDER BY m.avgRating DESC LIMIT 100
```

Layer 2 rejected it (`database_warnings`: the property `avgRating` does not exist). The error went back to the model, which then declined. Without the check, the query would have run and silently returned no rows. The rejected draft and the failed check are written to the API log (`docker compose logs api`). The response shows the final outcome (`attempts: 2`). `gpt-oss-120b`, asked the same question, computed the average from `RATED` instead. This case was found by searching for one: across the four runs above, `gpt-oss-120b` never produced a draft that a check rejected.

## Verified facts versus AI-generated text

| In the response | Source | Trust |
|---|---|---|
| `/ask` `rows`, `rowCount` | Neo4j, from the query in `cypher` | facts, but answering the question the query asks, which may differ from yours (Q17) |
| `/ask` `cypher`, `params`, `explanation` | the LLM | inspect them; `checks` lists every validation step they passed |
| `/ask` `resolvedMovies` | the server's full-text match | deterministic; `ambiguous` flags ties |
| `/why` `paths` | Neo4j (`app/services/paths.py`) | verified graph paths: this is the explanation |
| `/why` `summary` | the LLM, given only the paths | checked by `summaryCheck`: any number or genre not in the paths is listed, and `note` starts with `UNVERIFIED` |

## Cost and limits

On Groq's free tier, `gpt-oss-120b` allows about 8,000 tokens per minute and 200,000 tokens per day. One `/ask` call sends about 2,200 prompt tokens, so the API sustains roughly three questions a minute, and a full evaluation run (75,000 to 90,000 tokens for 33 to 42 questions) fits about twice a day. When the quota is reached, `/ask` answers 502 with `RateLimitError` and the rest of the API is unaffected.
