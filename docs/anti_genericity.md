# Appendix: our schema versus an AI-generated one

The brief asks us to compare our graph schema with one generated by an AI assistant from the same project description, and to explain where and why ours differs. This file holds the data-model comparison (Part A); the API and LLM parts can add their own sections.

## Data model (Part A)

### How the AI schema was obtained

* **Assistant:** ChatGPT, free tier, default model and settings, in a temporary chat (no memory, no custom instructions), 17 October 2026. The model did not name itself: its `MODEL:` line reads "MovieLens Recommendation Graph v1.0".
* **Input:** the project description only (use case, MovieLens files, the four endpoints, the recommended algorithms), with a fixed output format. Nothing about our schema was given.

<summary>Prompt</summary>

```text
I am building a "Movie Recommender in Production" project: a production-grade
recommendation service over a user/movie bipartite graph, using Neo4j 5, Python
and FastAPI, with the MovieLens dataset (ml-latest-small for development,
ml-25m for larger experiments). MovieLens provides movies.csv (movieId, title,
genres), ratings.csv (userId, movieId, rating, timestamp), tags.csv (userId,
movieId, tag, timestamp) and links.csv (movieId, imdbId, tmdbId).

The API must provide: similar movies (GET /api/movies/{id}/similar),
personalized recommendations (GET /api/users/{id}/recommendations),
community-based discovery (GET /api/users/{id}/discover) and a
popularity/centrality ranking (GET /api/movies/trending). Recommended techniques
are similarity algorithms, Louvain and PageRank. It also needs NL-to-Cypher and
a "Why was this recommended?" endpoint based on graph paths.

Propose the Neo4j graph schema. Do not ask me questions; make your own choices.
Reply with ONE fenced code block and nothing outside it, using exactly this
format: [MODEL / NODES / RELATIONSHIPS / CONSTRAINTS / INDEXES /
PRECOMPUTED / DESIGN CHOICES]
```

### The two schemas side by side

| | AI-generated | Ours |
|---|---|---|
| Labels | `User`, `Movie`, `Genre`, `Tag`, `Tagging` | `User`, `Movie`, `Genre` |
| Relationships | `RATED`, `IN_GENRE`, `CREATED`, `ABOUT`, `USES_TAG`, `SIMILAR_TO` | `RATED`, `IN_GENRE`, `TAGGED`, `SIMILAR` |
| Movie properties | ids, `title`, `ratingCount`, `avgRating`, `lastRatedAt`, `trendingScore`, `communityId`, `pageRank` | ids, cleaned `title`, `year`, `genres` list, `community`, `pagerank` |
| `RATED` properties | `rating`, `timestamp`, `ratingKey`, `preferenceWeight` | `rating`, `timestamp` |
| Louvain runs on | the user–movie rating graph | the `SIMILAR` graph (users derive theirs) |
| PageRank runs on | the undirected rating graph, users and movies | the `SIMILAR` graph, movies |

### Where we agree

The AI reached several of our decisions independently, which we read as confirmation rather than coincidence: ratings as `RATED` relationships with the rating and timestamp on them; `Genre` as nodes; uniqueness constraints on `userId`, `movieId` and `Genre.name` (with the same constraint names as ours); a full-text index on titles; `SIMILAR` precomputed by Node Similarity and capped at top-k per movie; "liked" meaning a rating of 4.0 or more; preserving who tagged which movie; and treating GDS results as derived data that can be recomputed.

### Where we differ, and why

| # | AI choice | Our choice | Why (evidence) |
|---|---|---|---|
| 1 | **PageRank on the undirected rating graph** | PageRank on `SIMILAR` | We ran the AI's version on our data: its movie ranking has a rank correlation of **0.968** with the number of ratings, and its top 5 is the most-rated list (*Forrest Gump*, *Shawshank*, *Pulp Fiction*...). On an undirected graph PageRank is close to degree, so it repeats the `ratingCount` the same schema already stores. Ours correlates at **0.145** with rating count: it measures how central a movie is among movies liked by the same people, which popularity does not tell. |
| 2 | **No `year`; title stored as given** | `year` parsed out (nullable), title cleaned, titles not unique | The year is inside every MovieLens title (`Matrix, The (1999)`). Without parsing it, "movies from the 1990s" needs a regex on every title, and 1,822 titles keep their article at the end, which neither users nor an LLM write. The AI does not mention that five titles are shared by different films (notebook 1.6), which rules out ever treating `title` as an identifier. |
| 3 | **Genres as nodes only** | nodes **and** a `genres` list | The nodes serve paths, explanations and GDS, as in the AI schema. The list avoids an extra expansion per candidate when a recommendation query only filters by genre. Both are written by the same statement, and a test checks they agree. |
| 4 | **Tags as `Tagging` event nodes plus canonical `Tag` nodes** (2 labels, 3 relationship types) | `TAGGED {tag, timestamp}` relationship | Both preserve who tagged which movie (the naive `User→Tag→Movie` design does not). The AI's version is more general, but costs two hops per tag and 3,683 extra nodes for a feature used by 58 of 610 users. A relationship property with an index answers "movies tagged X" in one hop. We would adopt the event-node design if tags became central (tag-based similarity, tag moderation). |
| 5 | **Louvain on the user–movie rating graph** | Louvain on `SIMILAR`, user community derived | We ran the AI's version: it works (9 balanced communities, largest 28% of nodes). We keep ours because (a) it gives a community only to movies with enough evidence (10+ likes), whereas the bipartite version assigns a movie rated once to the community of its single rater; (b) the communities come from the same similarity the `/similar` endpoint uses, so explanations stay consistent; (c) it runs on 11,820 relationships instead of 100,836 (52,660 instead of 1.27 million on the ml-25m sample). |
| 6 | **Stored aggregates**: `ratingCount`, `avgRating`, `lastRatedAt`, `trendingScore` | computed at query time | A count of relationships without a filter is read from Neo4j's degree store, so `ratingCount` costs nothing to compute and cannot go stale. `trendingScore` bakes a notion of "now" into the data and must be refreshed by a scheduled job; we keep recent activity as an indexed query on `RATED.timestamp`, anchored on the last rating (MovieLens ends in 2018). This is a trade-off: a stored score is faster to read, and the API benchmarks will tell whether we need it. |
| 7 | **`ratingKey` + relationship uniqueness constraint**, stored `preferenceWeight` | `MERGE (u)-[:RATED]->(m)` between constrained nodes; "liked" filtered at projection time | The constraint is supported by Neo4j 5.26 Community (we checked) and would also protect against concurrent writers. Our loader is a single sequential process, and an integration test proves re-running it creates no duplicate; adding a string key to every rating (1.27 million on the sample) buys protection we do not need. `preferenceWeight` stores a value that is a function of `rating`; we derive it in the projection query instead of storing it twice. |
| 8 | **`pageRank` and `communityId` on users too** | users get a community only | No endpoint ranks users, so a user PageRank would be computed and never read. |

### What we took from the AI schema

* **A full-text index on tags.** The AI indexes tag text for search. Our range index only matched exact tags, so we added `tagged_tag_fulltext` on `TAGGED.tag`: "dark" now finds *dark comedy*, *dark humor*, *dark hero* (covered by a test).
* **Evidence counts on similarity** (`commonUsers`). Worth exposing in the "why" endpoint as "liked by 23 of the same people"; it can be computed for the one pair being explained instead of stored on every `SIMILAR` relationship.

### Summary

The AI schema is a solid generic design and agrees with ours on the core. It differs where a decision depends on the data rather than on the description: what PageRank measures on this graph, the year and duplicate titles hidden in MovieLens titles, how sparse tags are, and how many likes a movie needs before its similarity means anything. Each of our differences is backed by a measurement on the dataset, and one AI idea was adopted.
